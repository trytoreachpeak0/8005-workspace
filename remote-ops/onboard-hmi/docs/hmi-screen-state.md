# 从控制端读车载端的屏幕状态快照

[onboard-hmi#316](https://github.com/trytoreachpeak0/8005-agv-onboard-hmi/issues/316)，2026-10-12。设计依据是车载端仓
`docs/W2G_HMI_OBSERVABILITY_RESEARCH.md`（w2g/fp-v2-impl）第 4.1、4.3、5、6、7 节，本票是其中的 T3。

## 这是什么

截屏（`17-capture-hmi-screen.ps1`）能回答「屏上画了什么」，回答不了「为什么这么画」。所以车载端在 T1a、T1b、T2
（onboard-hmi#313、#314、#315）里加了一份**屏幕状态快照**：从界面的 ViewModel 读出「此刻显示什么、哪些按钮能按」，
写成本机文件。控制端经现有 SSH 通道读这份文件，不开端口、不碰窗口。

车上有两份文件，与车载端技术日志同目录（默认 `C:\Users\HT\AppData\Local\SQCD\8005AGV\logs`）：

| 文件 | 内容 |
| --- | --- |
| `hmi-state.json` | 当前快照。内容一变就重写，内容不变也每个心跳（默认 5 秒）重写一次；写临时文件再一步替换 |
| `hmi-state-yyyyMMdd.ndjson` | 时间线，内容每变一次追加一行，按天分文件 |

**快照默认是关的**（用户 2026-10-12 定：先只在 agv02、agv03 的现场配置里打开，跑满一个现场周期再议默认值）。
没打开时脚本报 `ABSENT`。

`18-read-hmi-screen-state.ps1` 做两件事：

- **读取**：读当前快照，按车上的时钟判断它新不新鲜，打印摘要（横幅、显示中的按钮与能不能按、输入框、弹框、原始码）；
  `-TimelineLines N` 再列出时间线最后 N 行。
- **对照（`-CrossCheck`）**：读一次快照，用 UIA 读一次屏，再读一次快照；前后两次快照没变才比对，输出差异表。
  它是快照可信与否的唯一证明（调研第 6 节第 1 条）：快照只有在被证明与屏一致的范围内才可信。

## 结果码

所有时间都用**车上的时钟**判断（读文件时同一次 SSH 里取车上的「现在」），因为车与控制端的时钟曾差过几个月（`fleet.md`）。

| 结果 | 退出码 | 意思 |
| --- | --- | --- |
| `ACTIVE` | 0 | 快照在写，最近一次写入在 15 秒以内，写它的进程还在 |
| `DISABLED` | 2 | 快照因为自己的异常停用了（文件里记着停在哪个入口、什么异常类型）。车载端照常在跑，只是没有快照可看 |
| `STALE` | 3 | 写它的进程还在，但最近一次写入超过 15 秒：调度线程没在跑心跳，即**界面无响应**。时间在未来超过 15 秒也报这个（车上时钟被往回拨过，年龄没法判断） |
| `EXITED` | 4 | 文件写着 `ACTIVE`，但写它的进程已经不在了 |
| `ABSENT` | 5 | 没有 `hmi-state.json`：开关没开、车载端版本不含快照、或目录不对。车载端在跑时会提示「多半是没开」 |
| `UNREADABLE` | 6 | 文件在，但不是本脚本认识的格式（`schemaVersion` 不是 1、缺字段、不是 UTF-8 JSON） |
| `TOOL_FAILURE` | 1 | SSH 失败，或车上的回答解不开 |

`-CrossCheck` 另有四个：

| 结果 | 退出码 | 意思 |
| --- | --- | --- |
| `MATCH` | 0 | 比对了，没有差异 |
| `MISMATCH` | 10 | 比对了，有差异。按调研第 6 节，这时快照**不可信**，回退到截屏，差异当缺陷查 |
| `MOVING` | 11 | 屏在 UIA 读取前后变了（内容版本号或进程启动号不同，或者 UIA 读到的不是写快照的那个进程），不下结论 |
| `CAPTURE_FAILED` | 12 | UIA 读取没有得到完整的控件树（取屏失败、超时、节点数到上限、读到一半元素消失） |

第一次读快照就不是 `ACTIVE` 时，`-CrossCheck` 不取屏，直接以那次的结果收场。

### `STALE` 和 `EXITED` 怎么分

车载端正常退出时**不写结束标记**（onboard-hmi#315 剩余风险 L2），所以车载端一关，文件就停在最后一刻、仍写着
`ACTIVE`，单看文件分不出「界面卡住」和「程序已经退了」。脚本在同一次 SSH 里列出车上所有 `SQCD.Agv.Wpf` 进程，
按快照里的 `processId` 找写它的那个进程：

- 找不到 → `EXITED`；
- 找到了，但它的启动时间比快照记的 `processStartedAt` 晚 5 秒以上 → 进程号被别的进程重用了，也是 `EXITED`；
- 找到了 → 再看写入时间，超过阈值是 `STALE`，否则 `ACTIVE`。

进程退了而文件又恰好不旧（刚退出不到 15 秒），报的仍是 `EXITED`：进程不在了，谈不上卡住。

阈值 15 秒是出厂心跳 5 秒的 3 倍（调研 T3 验收的建议值）。现场配置若改了 `heartbeatIntervalMs`，用
`-StaleAfterSeconds` 跟着改。

## 只读

发到车上的只有一段脚本（`New-ReadScript`），它只做三件事：以只读方式打开两份文件、列出时间线文件、列出车载端进程。
不登记计划任务，不起停进程，不写车上任何文件，不改车载端配置。`-SelfTest` 用语法树逐条核对这段脚本里出现的每个命令和
每个 .NET 方法都在一张允许清单里，并核对唯一一处打开文件的调用是 `File.Open(路径, Open, Read, ReadWrite|Delete)`；
另有十几条探针（`Remove-Item`、`Stop-Process`、`Register-ScheduledTask`、`& schtasks`、拼出来的命令名……）证明这张清单
真能拦住。扫描看得到直接写出的调用，看不到经反射间接调用的方法，这一点与 `17` 的扫描同一边界。

车上的字节转成 base64 再传回控制端，不经过控制台代码页，快照里的中文不会变成 `�`（hmi#292 那次的坑）。

### 关于打开文件时的共享模式，有一处与预期不同

写出器每次写快照都是「写 `.tmp` → `File.Move` 覆盖 `hmi-state.json`」。读取者用 `FileShare.ReadWrite | Delete`
打开，是为了不挡这一步替换。**本机实测这并不够**（2026-10-12，Windows 11 26200，各跑 4 秒）：

| 读取者 | 替换成功 | 替换失败 |
| --- | --- | --- |
| 没有读取者 | 467 | 0 |
| 以 `ReadWrite, Delete` 共享，不停地读 | 114 | 97 |
| 以 `ReadWrite` 共享，不停地读 | 115 | 89 |

也就是说，只要读取者手里拿着句柄，替换就会失败，加不加 `Delete` 都一样。原因是 .NET 的 `File.Move` 用的是
`MoveFileEx`，不走 POSIX 语义的改名。真正兜住的是两件事：读取者持有句柄的时间极短（一次读约 0.2 毫秒），以及写出器自己
的重试（`HmiScreenStateFileWriter`：失败后隔 10 毫秒再试，最多 5 次）。

5 次都撞上的情况确实会发生：自检照写出器的重试规则复刻了一个写者，让读取者每秒读 50 次（实际用法是一次运行读一两次）。
普通优先级下 3280 次替换里 0 次放弃；经 `Invoke-HeavyLocal.ps1` 降为低优先级运行时，2064 次里放弃了 1 次。放弃一次的后果是
写出器在日志里记一行「写盘失败」，下一个心跳再写，也就是最坏丢一次心跳，不影响界面与业务。所以自检断言的是：读到的每一份
都是完整文件，并且**不会连续两次放弃**（读取者不会把写出器持续挡住）。变异验证里有一条让读取者持有句柄几十毫秒，这条断言
必须变红。

时间线文件是追加写，写出器以 `FileShare.Read` 打开它，读取者以只读、共享 `ReadWrite` 打开，两边兼容，不存在上面的问题。

## 对照比什么

| 项 | 快照一侧 | UIA 一侧 |
| --- | --- | --- |
| 横幅文字 | `banner.stateText` | 「手动提交」按钮**整棵子树之后**的第一个文本元素（横幅文字没有 AutomationId，`MainWindow.xaml` 里它紧跟在扫码行之后；按钮自己带一个同名文本子节点，要跳过） |
| 按钮可见 | `buttons[].visible`（绑定层可见） | 控件树里有没有这个按钮。WPF 把 `Collapsed` 的元素排除在控件树外 |
| 按钮可按 | `buttons[].enabled` | 按钮的 `IsEnabled`；只在两边都可见时比 |
| 「现场确认充不上」选项 | `options[].automationId` | `UnableToChargeOptions` 下的按钮，或同 AutomationId 的按钮 |
| 输入框可见、可编辑、是否为空 | `inputs[]` | `Edit` 元素；**只比是否为空，不读、不输出框里的内容** |
| 弹框 | `modals.depth`、`modals.open[].title` | 车载端进程可见的 `#32770` 窗口个数与标题 |
| 原始码 | `rawCodes[]`（可见与值） | 同 AutomationId 元素是否存在，及其 `ItemStatus` |

按钮按 AutomationId 找；没有 AutomationId 的按标题文字找，同一个标题找到两个就报一条差异，不猜是哪个。

**不比的**：说明行与操作员提示（提示到期那一刻快照比屏早一步，T1a 审查 L5 预先说明过）、倒计时文字、旅程计划行、
清单行、仓位卡、扫码框回车键的 `CanExecute`（UIA 读不到它）。

还有两处没有实测、只是推断：弹框弹着时主窗口按钮在 UIA 里的 `IsEnabled` 是否仍是快照里的值（推的：WPF 元素的
`IsEnabled` 不受 Win32 窗口禁用影响）；命令按钮的 `IsEnabled` 跟 `CanExecute` 之间是否有刷新延迟。这两处若在对照里
报差异，先看是不是这个原因。

UIA 一侧怎么取：

- 车上：调用 `17-capture-hmi-screen.ps1`（它会在车上登记一次性计划任务进交互会话，跑完注销，这是它自己的约定）。
  它的结果为 `CAPTURED` 或 `DESKTOP_LOCKED`（锁屏时窗口的控件树照样能读）才比对。
- 本机（`-Local`）：直接在当前桌面会话里运行 `17` 的车上半段 `agv-capture-hmi-screen.ps1`，按快照里的进程号读，
  不经 SSH、不登记计划任务；结果用 `17` 的同一条判定规则（从 `17` 的语法树里取出 `Get-CaptureOutcome`）。字段口径与
  车上完全相同，因为跑的就是同一个脚本。本票为此给车上半段的每个节点加读了 `ItemStatus`（只读属性）。

## 自检与变异验证

```bash
pwsh -File remote-ops/onboard-hmi/scripts/18-read-hmi-screen-state.ps1 -SelfTest
pwsh -File remote-ops/onboard-hmi/evidence/hmi316-20261012/mutate-18.ps1
```

自检离线，`ssh` 用一个替身（把编码后的读取脚本在本机对着临时目录执行），UIA 读取也用替身。覆盖：七个读取结果各自的判定
与边界（恰好 15 秒仍是 `ACTIVE`、进程启动时间在容差内外、`DISABLED` 压过进程已退出）、对照的每一类差异各一条、
`MOVING` 与 `CAPTURE_FAILED` 的各种来由、只读扫描、`agv01` 被拒且没有调用 ssh、端到端的每个退出码、证据文件与车上文件
逐字节相同、边写边读。变异验证把判据逐条改坏，每一条都要让自检变红：36 条全部抓住，过程与结果见
`evidence/hmi316-20261012/SUMMARY.md`。
